## 本地升级步骤

1. 在旧版管理页“系统设置→备份”创建一致性备份并执行备份预检，保留完整旧程序目录和该备份。不要手工复制运行中的 sqlite/WAL 组合。
2. 停止旧 daemon 和 bridge。确认原数据目录的 daemon.lock 已释放；不要删除活动锁或终止其他项目进程。
3. 将2.0候选解压到独立程序目录，校验归档SHA-256及manifest；继续显式指定原来的数据目录，端口沿用空闲批准端口。新程序首次遇到v1库会在同一数据目录 backups/pre-v2-*.sqlite 做一致性备份，然后事务追加migration2。
4. 启动包内运行时（macOS/Linux为 `./flowhub serve --data-dir '/绝对数据目录' --port 18473`；Windows为 `flowhub.cmd`）。重启后在管理页解锁Vault。恢复旧宿主身份令牌文件引用，旧execution客户端仍为七工具；新个人/编排身份为21工具。旧宿主缓存需要新建会话刷新目录。
5. 校验旧草稿/布局、不可变版本hash、历史报告、客户端及凭据状态。先用隔离数据目录与合成MCP验证新增功能，不将开发自测接入正式业务。

## 停机回滚

先停止2.0 daemon/bridge，保留当前2.0一致性备份及程序。使用当前程序的 `./flowhub restore --backup '/升级前备份.sqlite' --data-dir '/绝对数据目录'`，命令要求daemon已停，会保存被替换库的pre-restore副本。然后用原旧程序和同一数据目录启动，重新解锁Vault并核验历史报告与版本hash。2.0新增内容不会出现在升级前备份中，须留好2.0备份以便之后恢复。

禁止让旧程序直接打开已经迁移到v2的库；禁止删除新表或修改历史checksum降级。备份包含敏感业务与凭据密文，仅保存在本机。执行令牌和程序文件与数据库分离，必须保留匹配的数据目录其他文件。

`npm run test:upgrade-local` 在临时目录提取并编译基线45eed03的实际旧程序，运行旧v1库、生成报告和备份，然后启动2.0、检查所有旧行、备份预检、拒绝缺失新表、拒绝运行中恢复，最后停机恢复并重启实际旧程序。该脚本不读取正式库，也不运行安装器。macOS成功不代表原生Windows通过。

S7本机演练已通过：实际旧程序→v2→停机恢复→实际旧程序重启，旧业务行/发布hash/报告字节保持不变；记录在 `evidence/v2/S7-upgrade.txt`。原生Windows/企业策略仍未验证。

## alpha.2 审计修复兼容性

迁移1与迁移2的历史DDL/checksum保持原字节。本次加强实际表DDL、约束、虚拟FTS模块和shadow的只读校验；同列普通表替代FTS等损坏库会明确MIGRATION_MISMATCH，不能修历史或重建空库绕过。Vault口令轮换同时事务重包v2 Provider continuation及历史认证交付密文，任一损坏或写失败完整回滚。结果清理范围新增助手、自测和事件副本，必须预览范围/hash再提交；旧无任务归属消息的保守兼容范围见V2_USER_GUIDE。未自动清理用户数据。

本轮再次使用实际45eed03程序完成旧库创建→alpha.2升级→停机恢复→旧程序重启，旧业务行、发布hash和报告字节不变，见evidence/v2/audit/upgrade.txt。Windows与真实用户备份恢复仍属独立验收。

## 2026-11-02 工作流删除兼容性

删除使用既有 workflows JSON 记录中的 deletedAt/deletedBy，并置 enabled=false、语义 revision+1；不改任何表结构、冻结 DDL 或迁移 checksum。记录保留以防旧请求、旧 ID 和种子恢复重新创建同一工作流。发布快照、历史运行/产物、授权记录与凭据均不级联删除；仍由原生命周期策略管理。当前程序的备份/恢复保留这些 JSON 字段，离线 source snapshot 与 contracts 包含新增删除请求契约。旧版程序不认识 deletedAt，离线回滚应按原规则使用升级前备份，不能用旧程序直接重新启用已删除数据。

停机恢复或回滚后，先在浏览器中完整重新加载所有 FlowHub 标签页（例如 Cmd+R / F5），再解锁并核对恢复数据；不要只使用页面内部的“刷新”。完整重载会重新建立事件游标和列表状态。恢复前若有本地未保存内容，应先复制 DSL 和输入框中的未完成 JSON。本轮验证了重启/恢复后的新连接；旧标签页自动跨恢复世代切换尚未实现，不能将其算作验收通过。
