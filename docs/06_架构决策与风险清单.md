# MCP FlowHub 1.0：架构决策、风险与设计包边界

日期：2026-10-29。此文记录为何这样设计，防止后续Codex实现时为了“更自动化”破坏原始目标。

## 1. 架构决策记录

| ADR | 决策 | 不采用的方案 | 为什么 | 将来何时重评 |
|---|---|---|---|---|
| 001 | 一个MCP服务 + 固定七工具 + 动态工作流目录 | 每链路一Server/Tool | 解决配置膨胀，降低宿主上下文负担 | 若具体宿主需要动态工具性能优化再评估，默认不变 |
| 002 | Codex推理、Hub执行受控步骤 | 只有Prompt手册；Hub内置另一个全能Agent | 获得真实策略/证据，又不要求新LLM费用 | 无人值守需求明确且有模型预算时 |
| 003 | 本地单用户、Windows优先 | 首发SaaS、多租户和公网网关 | 适配企业内网与用户实际验证地点 | 第二个团队确认远程协作需求后 |
| 004 | 标准SDK v2 + 原生legacy兼容 | 手写两代协议 | 协议变更由官方适配；业务状态独立 | SDK实际兼容测试失败时，先复核不直接自造 |
| 005 | stdio薄桥 + 唯一daemon | 每个客户端运行独立引擎 | 防SQLite双写、重复调度和状态分裂 | IPC改进不会改变唯一引擎原则 |
| 006 | 不可变发布与run快照 | 运行自动追随最新草稿 | 可追溯、可恢复、避免审核后换参数 | 不变；只增迁移/显式新run |
| 007 | 强环境绑定、固定模板、只读授权 | env提示词、SQL正则、readOnlyHint | UI声明不能证明数据库权限 | 有受审计SQL策略引擎后谨慎扩展 |
| 008 | 人工批准独立管理权限 | Agent调用approve工具 | 防止自我授权与过期批准复用 | 不变，未来可对接组织审批系统 |
| 009 | MD/HTML优先、报告字节校验 | 默认承诺任意DOCX/PDF Skill远程调用 | 区分宿主声明和实际可验证产物 | 安全artifact导入完成后支持二进制 |
| 010 | 串行+互斥条件优先 | V1立即做循环并行子工作流 | 降低恢复、join、预算与审批复杂度 | V1稳定、真实需求证明后V1.1 |
| 011 | TS单语言 + SQLite | 为熟悉技术引入微服务/Redis/Kafka | 降低分发、维护和本机依赖 | 单机容量或组织标准确实成为瓶颈时 |
| 012 | 云端合成测试，公司本地真实验收 | 云端接生产数据库；家用电脑缺MCP就无法开发 | 分离通用产品和企业私有环境 | 不变，除非组织明确授权另一托管方案 |

## 2. 主要风险与应对

| 风险 | 可能性/影响（设计判断） | 早期信号 | 应对与退出条件 |
|---|---|---|---|
| 公司文件加密影响程序/SQLite/子进程 | 未知/高 | PoC包启动或重启失败 | S0先验证；采用IT批准路径，不绕过 |
| 现有数据库MCP无法约束资源/权限 | 中/高 | 同一凭证任意切库、自由SQL | 暂停真实生产发布；独立只读凭证或改造下游 |
| 宿主插件没有独立调用接口 | 中/中 | Hub拿不到标准endpoint/schema | 保留host任务或减少V1支持清单 |
| Codex没有自动选择正确流程 | 中/中 | 同名方案误选、环境缺失 | 改描述与检索，显式ID兜底；环境不明确必须问 |
| MCP新旧代际行为不同 | 高/中 | 只在一个SDK默认模式通过 | 独立兼容矩阵；只声明实测范围 |
| 缺少报告Skill或格式不稳定 | 中/中 | 只有路径没有字节、章节缺失 | 主路线MD内容提交；声明式模板降级 |
| 运行输出含敏感信息/注入指令 | 高/高 | 日志含token、SQL或“忽略规则” | 最小化/脱敏；内容不改变策略；企业批准模型路径 |
| 重试造成重复负载或副作用 | 中/高 | 超时后盲目再调用 | 明确OUTCOME_UNKNOWN；受控安全重试 |
| 整套UI完成但核心没有约束 | 高/高 | 仅toast和内存状态，自证测试 | 后端负向测试、独立协议Mock、真实验收门禁 |
| 依赖许可或供应链有问题 | 中/中 | 复制不明代码、浮动latest | lockfile、SBOM、按文件许可审核、禁止带公司凭证构建 |
| SQLite原生模块跨平台失败 | 中/中 | Linux过、Windows不能加载.node | Windows真实CI打包，不在目标机现场编译依赖 |
| 误把本地部署当数据完全本地 | 中/高 | 生产日志直接交给未获准云模型 | UI提示数据路径，组织批准，默认合成数据 |

## 3. 从设计包到第一轮开发的最短路径

1. 在自己的GitHub新建**纯通用代码**仓库；本次没有代你新建仓库或提交代码。
2. 放入本设计包的docs/contracts/examples，按任务书添加AGENTS模板；不要上传公司配置。
3. 只派发S0：最小daemon、一个固定工具集、stdio薄桥、一个Mock、Windows离线包。
4. 在公司批准设备和目录验证能运行、持久化、连接Codex与Mock；记录加密策略开启时行为。
5. 通过后分PR执行S1–S5。产品核心先打通，再将高保真原型逐步替换为真实功能。
6. 公司本机单独登记实际MCP，做试运行与生产只读验证。失败只回传批准后的脱敏摘要与合成复现。

将整个方案一次扔给Codex并要求“全部开发完不要停”不利于验收；任务书按阶段拆分，跨越公司权限门禁时必须等待真实记录。

## 4. 原型和样例不是生产实现

本交付包含产品/架构/协议/UI/测试/任务书、机器可读草案及可点击原型。没有实现真正的Hub引擎、数据库迁移、认证系统、凭证库、真实MCP连接或企业联调。

- UI原型的“已发布”“成功”“只读”“审批”均为模拟状态，不构成安全控制。
- JSON示例使用DEMO标识、example.invalid和placeholder摘要，均标模拟，不可直接发布真实生产流程。
- `workflow.schema.json`的结构检查不替代图语义、权限、SQL范围和数据库权限验证。
- 100个验收用例是**待执行测试设计**，不是100个已经通过的测试。
- 工期36–54有效人日是一个工程估算，取决于开发熟练度与复用情况，不承诺Codex一次生成或特定日历交付日。
- UI原型托管与文档下载只是本设计交付；实际企业使用版应在获准设备/网络运行。

## 5. 许可与复用原则

建议通用代码自主实现，以官方SDK、React Flow等基础组件构建。借鉴其他项目的产品流程、架构与公开规范，不等于禁止一切二次开发；是否可以复制/改造具体代码，要按对应文件和锁定版本的许可证判断。

拟采用MIT或Apache-2.0等许可发布你独立拥有版权的代码；最终由维护者决定。第三方代码保留原许可/NOTICE；含AGPL、SUL或商业组件的代码不能未经审核混入后再统一改标MIT。“免费放GitHub”本身不免除任何许可条件。此处是工程合规提醒，不代替具体许可证审查。

本次未进行任何竞品完整源码安全审计，也未把竞品代码作为实现交付。正式开发PR需要维护 `THIRD_PARTY_NOTICES`、依赖清单和必要来源记录。
