# FlowHub 悬浮对话助手设计方案

按 Codex 的逐轮对话方式组织内容：用户发一条消息，助手在这条消息下面回答，下一次追问沿用这段会话。入口是各页面右下角的小图标，点击打开紧凑聊天窗。聊天正文优先，工具活动和来源按需展开。

设计阶段交付了方案、设计图和离线交互原型。用户随后批准实施，正式代码与验证见[实施记录](实施记录.md)。本目录HTML原型仍使用示例数据，不调用模型、MCP或管理API。

## 设计参考

| 参考 | 可核对的官方展示 | 本方案采用的部分 |
|---|---|---|
| Codex 的聊天与项目上下文 | [Projects and chats](https://learn.chatgpt.com/docs/projects) | 独立会话、持续追问、当前选择提供上下文；按用户指定的Codex体验组织逐轮对话 |
| Intercom Messenger | [官方设置与展示](https://www.intercom.com/help/en/articles/6612589-set-up-and-customize-the-messenger) | 右下角启动图标；点击后直接进入会话；收起后保留会话；不先展示复杂导航首页 |
| Zendesk Messaging Widget | [官方外观与位置展示](https://support.zendesk.com/hc/en-us/articles/4500747797914-Configuring-the-name-and-appearance-of-the-Web-Widget) | 独立launcher和聊天窗、紧凑标题栏、用户消息与助手回答的视觉区分、边距及圆角 |

以上是交互原则的借鉴。下文尺寸、布局、数据处理和验收要求是针对FlowHub的设计选择，不是对参考产品规格的转述。

## 当前问题及影响

通过用户截图和当前源码可以确认：

- `AssistantPanel.tsx` 将会话、上下文、模型、模式和消息堆在一个长页面，用户主要看到表单与任务记录。
- 回复使用普通文本段落，Markdown没有按语义展示，`**加粗**`等标记直接暴露。
- 工具回执使用默认展开的details，整段JSON占据正文；最新任务独立于历史消息展示，缺少清晰的每轮归属。
- MCP能力查询为空时，回复仍可能引用帮助文档里的“固定21工具”，没有直接回答当前已连接或已发现的MCP。
- 当前系统提示较笼统；每轮先检索帮助文档，没有为“当前状态”问题建立明确的运行时事实优先级。对错误回答的判断来自截图及这条调用链，不把所有问题归因于模型本身。

因此，改造同时覆盖聊天界面和回答依据，不能仅把现有长表单装进小窗。

## 页面和尺寸

### 桌面

- 全局悬浮按钮：54 × 54 px，距右侧、底部各24 px；使用FlowHub标识，不使用大型机器人插画。
- 默认聊天窗：420 × 652 px，右侧24 px，底部92 px。高度随可用视口缩小，保持完整输入区。
- 无遮罩、不推动主页面布局；主页面仍可操作。收起后仅保留小图标，不自动弹开或播放提示音。
- 标题栏仅保留助手名称、历史、新建和收起。模型选择放在输入框底部，不展示配置表单。
- 当前页面用一个可移除的小标签展示。工作流和运行详情通过当前页面传入，不要求手填ID。

### 手机

- 悬浮入口保留；展开后使用接近全屏的底部面板，避免420 px小窗被挤压。
- 标题栏和输入区固定，消息区独立滚动；适配安全区和软键盘，输入文字至少16 px。
- 收起时恢复原页面位置；未发送的输入和会话保留。

### 聊天正文

- 用户消息靠右，浅灰消息背景；助手回答靠左，轻量标识和清晰正文，不给每句回答再套厚重卡片。
- 支持安全Markdown：段落、加粗、列表、链接、代码。禁用模型原始HTML，不显示未渲染的Markdown标记。
- 一轮由“用户问题→这一轮的回复→可折叠活动/来源/动作”组成。后续轮次紧接着排列。
- 默认隐藏JSON、任务ID、修订号、token用量和工具参数。需要排查时从该轮“活动/详情”展开，不永久移除这些证据。

## 一问一答的行为

| 场景 | 用户看到的表现 | 必须保留的真实行为 |
|---|---|---|
| 输入并发送 | 用户消息立即进入对话，助手原位开始回复 | 接受回执后绑定taskId；请求失败仍保留用户消息，不丢输入 |
| 持续追问 | 继续回答同一话题，不重新创建任务表单 | 持久化同一会话，按允许的上下文范围提供近期对话；不能每轮只发送孤立问题 |
| 查询工具或页面信息 | 简短显示“正在读取MCP目录”等可观察活动，随后给结论 | 活动必须来自真实调用，不能伪造进度或展示私有推理过程 |
| 回答完成 | 正文、必要的下一步和紧凑来源 | 工具返回值是事实依据，不采用模型自报成功 |
| 修改草稿 | 正文说明修改结果，提供“查看改动 / 撤销” | 复用共享AuthoringService、原子operations、CAS及幂等；不恢复人工审批 |
| 只要方案、解释或建议 | 仅在对话中给方案和说明 | 不把这类请求误当成保存、发布或执行授权 |
| 用户明确要求发布或运行 | 在同一段对话给实际结果 | 保持既有owner、环境及执行边界，不另加逐步确认 |
| 停止回复 | 停止按钮替代发送按钮，保留已有内容 | 请求真实取消；已完成动作及回执保留，不重复调用 |
| 网络中断、重试 | 本轮内显示失败原因与重试按钮 | 原接受请求用原幂等key恢复；SSE游标重连，不再次执行写操作 |
| 收起、重开、切换页面 | 会话和未发送输入仍在；有新回复时仅显示小徽标 | 收起不取消后台任务。会话存活独立于页面组件挂载 |
| 向上查看历史 | 不强制跳到最底部；显示“有新回复”入口 | 用户位于底部时才自动跟随流式输出 |
| 没有模型 | 一条简短说明和“前往模型设置” | 无Key的发现、画布、Codex路径仍可用，不显示伪造回复 |

输入区只保留文字、模型入口、发送/停止。Enter发送，Shift+Enter换行，中文输入法组字期间不触发发送。Esc收起并将焦点还给悬浮按钮。普通聊天不再要求手动选择“帮助/编排模式”。

## 回答质量的改造

### 实时事实优先

“当前MCP有哪些”“这个流程哪里报错”等问题先读运行时事实，再在有必要时补充帮助资料。仅检索文档不能回答当前连接状态。

MCP清单需要明确区分：已登记连接、已发现工具、宿主专用能力、FlowHub对外固定工具。内部只读聚合服务应返回来源、启用/可用状态、最近扫描状态及时间，不需要新增MCP Server或扩大固定工具集合。

- 已查到数据：直接列出实际名称、状态和来源，避免回答泛泛的产品介绍。
- 已完成查询但目录为空：说明“当前还没有已发现的工具”，同时解释是否尚未扫描。
- 未扫描、查询失败或信息不足：标为未知，不用0项代替未知。
- 只有用户询问FlowHub对外接口时，才解释固定21工具及兼容7工具身份。
- 只读扫描与业务工具执行分开；助手不能为回答清单问题擅自调用真实业务查询。

### 示范对话

> 你：当前MCP有哪些？
>
> 助手：当前还没有已发现的MCP工具。目录尚未同步，不代表Codex没有配置。可以先进行只读发现。〔前往Codex发现〕
>
> 你：这会影响现有配置吗？
>
> 助手：不会。只读取Codex配置，不修改源文件，也不执行业务工具。

以上是空目录状态的设计示例。正式回复要依据实际查询状态，不能把这段文案固定用于所有用户。

### 连贯对话与上下文

- 保留当前项目、当前会话及本轮关联的信息；代词如“这个”“继续刚才”应解析到当前允许的上下文。
- 切换页面时保留可见历史，但不静默向模型发送其他运行的业务内容；当前页面标签清楚展示本轮范围。
- 沿用已实现的任务/消息来源绑定、模型配置隔离和owner检查。切换模型或运行时不能借“连续聊天”旁路这些约束。
- 模型名称使用配置名与实际model，不把内部UUID放在每句回答上。旧历史缺来源时保留阅读能力，不伪造其来源。
- 每条结论与本轮数据回执绑定。引用来源仅在有关时展示，答案主体先回答用户问题。

## 实施结构

建议拆出 `FloatingAssistant`、`ChatWindow`、`ConversationView`、`TurnMessage`、`ChatComposer` 和 `TurnActivity`。全局的会话状态管理器负责请求、SSE、取消和恢复；悬浮按钮只负责展开状态，避免收起窗口就卸载任务订阅。

继续复用assistant session/task/message/tool ledger、ModelProfile、共享Authoring和现有SSE。按taskId将用户消息、助手文本、活动和动作回执聚合成Turn视图；为会话分页增加批量只读投影，避免每条消息都请求一次任务详情。优先增补JSON元数据或只读视图，确需DDL时仅追加迁移，不能改变已交付checksum。

后端增加只读项目状态聚合，将当前连接/能力/扫描信息提供给助手。对问题类型建立“实时状态→相关工具→相关文档”的取证顺序。最终自然语言回复根据真实结果生成，空结果与查询失败使用不同的明确状态。

原AI工作台改为可选的会话管理/大视图；日常入口统一为全局悬浮按钮。画布里的AI按钮唤起同一个聊天窗，并携带当前节点，不创建另一套聊天状态。

## 实施顺序与验收

1. 统一会话与Turn视图，完成悬浮入口、聊天排版、Markdown、流式、发送/停止、收起恢复及移动端；保留现有记录。
2. 同批打通真实状态问答与连续追问，尤其验证本次截图中的MCP清单问题；不能仅以新外观作为完成标准。
3. 迁移草稿修改、撤销、来源与诊断到每轮折叠区域，补取消、幂等、并发编辑与页面切换回归。

拟定验收条件：

- 任一页面可打开，默认主界面只出现一个悬浮入口。
- 正文按轮次排列，不出现默认展开的工具JSON或全屏任务表单。
- 连续追问保留话题；未知/空/失败目录各自正确回答。
- 收起、重开、页面切换和刷新不丢持久化消息；关闭不重复触发任务。
- 发送丢回执、SSE断线、重试与取消不重复保存/执行。
- 明确“只解释”“给方案”“不执行”时无写入或运行；明确修改时提供真实改图回执。
- 1440/1366桌面及390/320窄屏可用；输入法、键盘、焦点和软键盘场景有实际验证。
- 用已配置模型完成真实的MCP清单问答、三轮连续追问、草稿解释与一次明确修改，并保留实际证据；不能用原型示例冒充实现通过。
